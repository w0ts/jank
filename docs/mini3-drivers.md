# Jank mini 3: the drivers still to write (plan, 2026-11-19)

Board `lcd2` = the Waveshare ESP32-S3-LCD-2 on the jank-mini-3 carrier. Nothing here has run on a board; the board is not ordered, so every pin is provisional.
Pin sources: **B** = `firmware/main/board.h` (lcd2 block), **P** = `hardware/jank-mini-3/parts.py` GPIO table (the source of truth), **D** = `docs/lcd2.md`, **R** = `hardware/jank-mini-3/README.md`.
Rules kept by every row: core 1 is the MIDI clock's alone (every task pinned to core 0; the Link library and the bridge task are on core 0); nothing writes to the hardware from here (the owner flashes); host tests are C and node, run by `tests/run.sh`.

## Where the sources disagree

- No pin disagrees between B, P and D for rows 1 to 7 (checked one by one: GPIO 4, 2, 15, 7, 8, 18, 10, 17, 13, 9, 5, 11, 6, 16, 21). Only wording differs: D says GPIO47 / 48 sit on "J20's pads", P also puts them on J16.5 / J16.6.
- Same GPIO number, different job: the XIAO bench CLK / RST (`board.h`: 2 / 1) against the mini 3's RST 2 / CLK 15 (row 2). GPIO1 is the lcd2's backlight.
- The cell's divider: mini 2.2 is x2 (`BOARD_CELL_DIV`), the LCD-2's is x3 (200 k / 100 k, D).
- `docs/linein.md` and `linein.c` describe the older analog input; `hardware/mini2/README.md` and `parts.py` have the differential one (row 3).
- `pump.c` and the `usbport.h` comment still talk about a charge pump for CLK / RST: gone since 2026-11-15 on mini 2.2 and never on the mini 3.
- Plug-detect polarity of LIN_DET (board.h mini 2.2: low = no plug) is inferred for the mini 3 from the parts (R37 / R38); the jack's switch wiring was not read.

## Order, and why

1. **Safe idle levels and V5_EN** (row 1, plus HOST_EN low, CLK / RST low): decides what is powered and driven. First, it changes nothing the board does not already do (R131 holds it on), and every later driver needs a known state. Host-testable decision, scope-check on the board.
2. **VBUS sense + battery sense** (rows 4, 6, inputs only): cannot hurt anything; the cutoff of row 1 and the host decision of row 5 need them; the screen's battery and plug icons start to show real values.
3. **CLK / RST** (row 2): a small change in code that already exists and is measured on the XIAO; needs row 1 (U21 powered). Check on the board that the MIDI clock's lateness (ABOUT: CLOCK LATE) does not move.
4. **LINE IN + plug detect** (row 3): the largest piece (the differential path is new code) but input only, and it can be built host-first.
5. **USB host** (row 5): last of the active ones, because it needs V5_EN (row 1), the VBUS sense (row 4) and is the only driver that puts a voltage on a connector another person plugs gear into.
6. MIDI TX2 is only a scope check; IMU and TF card: nothing.

## Decisions (owner, 2026-11-19)

1. **CLK / RST: short pulses, like Mutable Instruments Grids.** Every output pulse is high for about 1 ms (Grids: `kPulseDuration` 8 ticks of an 8 kHz timer = 1 ms, all outputs cleared together). CLK pulses once per clock step, RST pulses at step 0. Velocity and accents are ignored. Both pins idle LOW.
2. **Low cell: warn only**, on the screen. The firmware never cuts the 5 V rail (V5_EN stays high), so row 1 has no cutoff.
3. **USB host: a computer or charger on the LCD-2's USB-C (VBUS sense) always wins**: device mode, HOST_EN low. Only with the USB menu = HOST and nothing plugged in does the Jank drive the OUT port.
4. **LINE IN is not balanced audio.** The "differential" input of the hardware README is a ground-sensing difference, not a symmetrical connection: the jack is an ordinary stereo jack. Checked against `parts.py` (R30 / R31 / C30 / C31, R65 / R66 / C65 / C66, R32 / R67, R33 / R34, C32 / C67) and `hardware/mini2/README.md` ("The digital LINE IN"): tip and ring (L and R), each 20 k + 1 uF, mix into node A (LINE_IN, GPIO7); the jack's sleeve (ground, to the board's ground through 100 ohm, R39) goes through two 20 k + 1 uF branches into node B (LINE_SENSE, GPIO8); both nodes sit on the same 1.467 V bias. The firmware subtracts B from A, so the hum a ground loop puts on the sleeve cancels. The board does what the plan says, no disagreement. **First version: node A alone** (the L + R mix), so audio works; the A - B subtraction is a later step with host tests.
5. **IMU and TF card: out of scope.**

## Step 2 done: VBUS sense and battery sense (inputs only, 2026-11-19)

- **VBUS sense:** `BOARD_VBUS_SENSE_GPIO 10` for lcd2 (parts.py VBUS_SENSE, ADC1 channel 9, 3.0 V at 5 V). The code that reads it was already right for this pin: `usbrole.c` `input()` is a plain digital input with no internal pull-up or pull-down (the board has its own divider), and `usb.c` hands the pin to esp_tinyusb's VBUS monitor. High = a computer or charger on the LCD-2's USB-C. It shows where it already did (`usb` in the status key and HOME, `s_snap.usb.vbus`). Nothing acts on it yet (the host decision is step 5).
- **Battery sense:** `BOARD_CELL_GPIO 5` (the LCD-2's BAT_ADC, ADC1 channel 4), `BOARD_CELL_DIV 3`, `BOARD_CELL_EMPTY_MV 3300`. No line in driver on lcd2, so `linein.c` has a small branch (`linein_cell_step`, called from `uis_sys_step`, the ui task on core 0): ADC1 oneshot, 12 dB, 16 samples averaged, eFuse curve-fitting calibration when present (else the nominal 3.1 V scale), every 5 s (first read at the first step). Nothing runs on core 1 or in the beat path. The result is `linein_batt_pct()`, the same value the screens already read (`s_snap.batt_pct`: battery icon, amber under 30 %, red under 15 %: the low-battery warning). No UI, setting or cutoff was added; V5_EN stays high.
- **Percent and fitted:** the pure functions are `jl_cell_pin_pct` (pin mV x divider) and the existing `jl_batt_pct` (core/jank_line.c, host tests in `tests/test_line.c`). Fitted = the cell is at least `JL_NO_CELL_MV` 2000 mV, i.e. 667 mV at the pin (the rule mini 2.2 uses); below it the percent is -1, so no cell never shows as a low cell. 4.2 V = 1400 mV at the pin = 100 %; 3.3 V = 1100 mV = 0 %.
- **Only the real board can show:** the divider's accuracy (resistor tolerance, the 300 k source impedance into the ADC: a 100 nF at the pin may be needed), what the pin reads with no cell fitted (R20 should pull it to 0 V; unverified: the charger may hold VBAT up on USB power, which would read as a fitted cell), the 1.4 V level at 4.2 V against the 12 dB range, the readings while charging (high), and the VBUS level at 5 V and 4.35 V with ADC1 in use.

## Step 3 done: CLK / RST outputs (2026-11-19, host tests only, nothing run on a board)

- **Design:** `core/jank_clockout.c` (pure): per tick, whether CLK and RST go high now; `JCO_PULSE_US` 1000. `midi.c` (lcd2 only, `BOARD_CLK_GPIO >= 0`): `pulse_pins()` in `on_alarm` sets the pins high with `gpio_ll`; a second gptimer one-shot (core 1, interrupt priority 2, below the clock's 3) is armed in the same call (counter reset, alarm = 1000 us) and its IRAM callback `on_low` clears both pins. No task, no polling; the clock's own alarm (`arm()`) is not touched. Added time in the tick interrupt: on a tick with a pulse two GPIO writes, a counter reset and an alarm write (about 1 to 2 us, an estimate; check `midi_busy_cycles` / CLOCK LATE on the board); on other ticks a lookup. The XIAO bench code (`bench_pins`) is unchanged.
- **Division:** the CLOCK RATE setting (`s_prefs.rate`, pushed by `midi_set_clk_rate`) maps 1/4, 1/8, 1/16, 1/32, 24 PPQN to 24, 12, 6, 3, 1 ticks per step. Steps count from the Start, on the beat grid (every step length divides 24), so a rate change keeps the grid.
- **RST:** one pulse with the first clock after a Start (together with CLK, step 0); a Start while running pulses again; nothing while stopped.
- **Polarity:** no inversion needed. `parts.py`: U21 pins 1 to 2 and 3 to 4 are CLK_IO to CLK_B to CLK_N (two gates in series), RST_IO to RST_B to RST_N through pins 5 to 6 and 9 to 8; CLK_N / RST_N go through BAV99 and 2 x 1k to the jack. Two inverters = no inversion: pin high = jack high, pin low (power_early_init, 100 k pull-down) = jack idle low.
- **Idle:** `pulse_pins_up()` sets level, then direction, then level again (no glitch); power.c is unchanged.
- **Only the board / a scope can show:** the real pulse width and the jack level into a modular input, the interrupt's added time, that CLOCK LATE does not move.

## Step 5 done: USB host for the OUT port (2026-11-19)

- **Code:** `usbport_mini3.c` (the port HAL, `BOARD_USBPORT_MINI3 1` in the lcd2 section of board.h; 0 elsewhere), `core/jank_usbhost.[ch]` (the pure gate: HOST_EN, the role), `tests/test_usbhost.c`. `usbport.h` got one field (`poll_ms`: the role task reads this port every 20 ms instead of every 500 ms; 0 = as before) and `usbrole.c` one changed condition for it; the XIAO and the mini 2.2 have `poll_ms` 0, so their paths are unchanged. The role core (`jank_usbrole.c`) is untouched: the HAL reports "a computer or a charger" as `cc host` (device stack, nothing sourced) and "nothing on the LCD-2's USB-C" as `cc device` (host stack allowed, the 5 V signal after `prep_ms` 100 ms).
- **Wiring read from `parts.py` (nets quoted):** `HOST_EN` (GPIO17, J15.5; R91 100 k to GND) -> U21 pin 11 -> two of its inverters (pins 10 / 13, `HOST_M`) -> pin 12 `HOST5G` -> JP13 -> `HOST5` -> R93 680 -> D16 (BAT54C) -> `VUSB` = J4's VBUS pads A4 / B9 (C28 1 u to GND); `HOST5` -> R160 / R161 56 k (Rp) -> `CC2O` / `CC1O` = J4's CC. U21 (74AHCT04) is supplied from `V5C`, which is the 5 V boost's rail (`V5A`) through JP9; V5_EN (GPIO4, JP10 to the boost's enable, R131 pull-up) feeds it. So **there is no power switch for the device's VBUS**: HOST_EN high is a logic level through two inverters and 680 ohm (a short on J4's VBUS draws about 6.6 mA); it is also the Rp "source" sign on CC. With HOST_EN low both go to 0 V. JP9, JP10, JP13 are in `parts.py`'s DNP set (solder jumpers): whether they are bridged on the first boards is not verified here, so check by meter that HOST5 follows HOST_EN. J1 (TO ESP): VBUS pads `J1_VBUS1` / `J1_VBUS2` are open nets, no CC pins connected, D+ / D- on `UDP` / `UDN` shared with the S3 and J4.
- **Decision rules and timings:** see docs/usb.md "jank mini 3". HOST_EN: low at boot, low in the same 20 ms step as a high VBUS sense read, low on the setting DEVICE / `vbus_on(0)` / before any restart (`esp_register_shutdown_handler`); high only with HOST + VBUS sense low 500 ms (`JUH_DEBOUNCE_MS`) + V5_EN on 100 ms (`JUH_V5_SETTLE_MS`) + the role core asking. V5_EN cannot be read back (an output), so the gate trusts `power_early_init`; with no `BOARD_V5_EN_GPIO` HOST_EN never rises.
- **If a charger or computer goes into J1 while hosting:** J1's VBUS and CC are not connected to anything, so nothing is back-fed into our rails or the LCD-2 through J1. A C-to-C source sees no Rd and gives no VBUS. A plain A-to-C charger puts 5 V on open pads and its D+ / D- (often shorted together) onto `UDP` / `UDN`, which disturbs the data lines but is not a power path. A computer or charger on the LCD-2's own USB-C is the case VBUS sense sees: HOST_EN drops at once, the device stack follows. A cable swapped (J4 to the LCD-2's USB-C) would put the 680 ohm signal on the LCD-2's VBUS: VBUS sense then reads high, HOST_EN drops, VBUS falls, and after 500 ms it tries again (a slow cycle, harmless; seen only on the board).
- **Only the real board can show:** the VBUS sense levels with a computer, a charger and nothing (3.0 V expected at 5 V against the S3's input-high level; the esp_tinyusb VBUS monitor shares the pin with soft hysteresis, 1.7 V up / 1.4 V down); how quickly VBUS sense falls after an unplug (C29 10 n with 10 k / 15 k: microseconds, but the LCD-2's own VBUS capacitors and charger decide); the 5 V rail's real start-up (the 100 ms is a guess, power_early_init has run seconds before in practice); the voltage on J4's VBUS pads with HOST_EN high (about 4.2 V into a 10 k load; the BAT54C drop and the gear's own VBUS-detect threshold decide whether a device enumerates); that gear sees Rp 56 k and enumerates through J1 / J4 and the cable; whether the S3's D+ / D- behave with J1 / J4 on the bus while a computer is on the LCD-2 (they share the lines); whether JP9 / JP10 / JP13 are bridged.
- **Bench checklist, first power-up (meter; mots does it, nothing here touches the board):** 1. Power from the LCD-2's USB-C alone, no cable in J1 / J4, setting DEVICE (the default): HOST_EN (J15.5) 0 V from power-up on, HOST5 0 V, J4 VBUS (A4 / B9) 0 V, CC1O / CC2O 0 V; V5C 5 V. 2. Same with a computer on the LCD-2: all still 0 V; J4 VBUS stays 0 V. 3. Unplug it, set `usb host` (restart): after about 1 s HOST_EN 3.3 V, HOST5 about 5 V, J4 VBUS about 4.2 V (no load) or the value with a 10 k load, CC1O / CC2O about 5 V through 56 k. 4. Plug a computer into the LCD-2's USB-C while hosting: HOST_EN, HOST5, J4 VBUS fall within a few tens of ms, before the restart; the board comes back as a device. 5. Unplug: after about 0.5 s plus a restart, step 3 again. 6. Setting back to `usb device`: all 0 V. 7. Probe HOST_EN while switching the setting repeatedly and while knocking the USB-C plug: no spike above 0 V while VBUS is present. Stop at the first deviation.

## Step 4 done: LINE IN, node A alone, and the plug detect (2026-11-19)

- **board.h (lcd2):** `BOARD_HAS_LINEIN 1`, `BOARD_LINEIN_GPIO 7` (ADC1 channel 6, from the IDF channel table), the cell stays `BOARD_CELL_GPIO 5` (channel 4) and is now read in the continuous pattern [LINE IN, cell] like the mini 2.2; `linein_cell_step` is then the empty function (it is compiled only where there is no line in), so the cell is sampled in one place. `BOARD_LINESENSE_GPIO 8` is defined and not used. `BOARD_LINE_DETECT_GPIO 18`.
- **linein.c needed no change** (it takes the channels from the GPIOs by `adc_continuous_io_to_channel` and requires ADC1; no other hard-coded channel; one comment edited). 24 us per channel: the pattern is still two ADC1 channels at 83,333 Hz.
- **Plug detect polarity:** high = a plug, the same as on the mini 2.2 and what `jur_line_step` expects (raw nonzero = plugged). Evidence: `parts.py` R38 1 M to 3V3 on LIN_DET, R37 100 k from the ring to ground, the mini 2.2 README "J7's ring switch"; the part is a switched jack (PJ-307C). The datasheet's pin 3 = the ring-break switch is **inferred, not read**.
- **Source:** AUTO = the line in with a plug, else USB audio: the existing `usbrole.c` code, now with a real pin.
- **Not done:** A minus B (the later step: sample node B on ADC1 channel 7, a three-channel pattern would change the 24 us rule: to be derived and tested first).
- **Only the real board can show:** the bias level (expected 1.467 V, code about 1940), the noise floor, clipping level, that LIN_DET reads low with no plug and high with one (and its rise time through the 1 M with the pin's capacitance), the hum with a ground loop, and any clock-edge noise on the ADC.
- **Link problem SOLVED (2026-11-19): bridge.c's 20 frame slots (30 KB) are allocated in PSRAM on the lcd2.** Without it `dram0_0_seg` overflowed by 6,472 bytes (LINE IN adds about 13.2 KB: linein.c bss 7.8 KB, the 16-frame ring 6,784 B, and 4.9 KB of interrupt-safe driver code in IRAM, which moves the start of DRAM up). `board.h` lcd2: `BOARD_BRIDGE_SLOTS_PSRAM 1` (0 elsewhere); `bridge.c`: `s_slot` is then a pointer filled in `bridge_start` by `heap_caps_calloc(SLOTS, ..., MALLOC_CAP_SPIRAM)` (no PSRAM = `ESP_ERR_NO_MEM`, as the other stores). Safe because only tasks touch the slots (Wi-Fi task `on_air` / `on_network`, TinyUSB task `on_usb` / `on_usb_tx_done`, the bridge task), never an interrupt or an IRAM-safe path; NCM copies the frame out in `tud_network_xmit_cb` (a CPU memcpy in the TinyUSB task), so no USB DMA reads the slots. Cost: a frame copy goes through the PSRAM cache (about 1.5 KB per frame, once in, once out). Measured by the linker map (static DRAM free = `dram0_0_seg` end minus `_bss_end`): lcd2 on main before LINE IN 5,576 B (`.dram0.bss` 195,208, `.dram0.data` 47,528, `.iram0.text` 108,643); LINE IN without this overflowed by 6,472; with it **23,816 B free** (`.dram0.bss` 172,472, `.dram0.data` 47,676, `.iram0.text` 112,983). XIAO: sections and `_bss_end` identical to main (same section sizes; `jank.bin` differs only in its build header). `CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY` was tried and not used (it also moves all of lwip's bss to PSRAM). `CONFIG_ESP_WIFI_RX_IRAM_OPT=n` was not needed and not applied.
